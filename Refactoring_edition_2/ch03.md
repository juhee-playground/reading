# 3장 코드 스멜 정리

## 3.1 기이한 이름

- 코드는 단순하고 명료하게 작성해야 한다. ⇒ 이름
- 이름 짓기
    - 함수 선언 바꾸기(함수 이름을 바꿀때도 사용)
    - 변수 이름 바꾸기
    - 필드 이름 바꾸기
- 마땅한 이름이 떠오르지 않는다면 설계에 더 근본적인 문제가 숨어있을 확률이 높다.
- 혼란스러운 이름을 잘 정리하다 보면 코드가 훨씬 간결해진다.

## 3.2 중복 코드

- 똑같은 코드가 여러 곳에서 반복된다면 하나로  통합하기
- 똑같은 표현식을 사용하는 경우 ⇒ 함수 추출하기
- 코드가 비슷한데 완전히 똑같지 않다면 ⇒ 문장 슬라이드하기
- 같은 부모로부터 파생된 서브 클래스들에 코드가 중복되어 있다면 ⇒ 메서드 올리기

## 3.3 긴 함수

- 짧은 함수로 구성된 코드 ⇒ 간접 호출의 효과
- 이해하고 공유하고 선택하기 쉬워진다 ⇒ 함수를 짧게 구성할 때 나오는 것.
- 함수 이름
    - 동작방식이 아닌 의도가 드러나게 짓기
- **무엇을 하는지**를 코드가 잘 설명해주지 못할수록 함수로 만드는게 유리
- 코드가 단 한줄이어도 따로 설명할 필요가 있다면 함수로 추출하는게 좋다.

## 3.4 긴 매개변수 목록

- 매개변수 목록이 길어지면 그 자체로 이해하기 어려울 때가 많다.
    - 종종 다른 매개변수에서 값을 얻어올 수 있는 매개변수가 있을 수 있는데 ⇒ 매개변수를 질의 함수로 바꾸기(11.5절)
    - 사용중인 데이터 구조에서 값들을 뽑아 각각 별개의 매개변수로 전달 하는 코드 ⇒ 객체 통째로 넘기기(11.4절)
    - 항상 함께 전달되는 매개변수들은 ⇒ 매개변수 객체 만들기(6.8절)
    - 함수의 동작 방식을 정하는 플래그 역할의 매개변수 ⇒ 플래그 인수 제거하기(11.3절)
    - 클래스는 매개변수 목록을 줄이는데 효과적인 수단이다. 여러 개의 함수가 특정 매개변수들의 값을 공통으로 사용할 때  ⇒ 여러 함수를 클래스로 묶기

## 3.5 전역 데이터

- 전역 변수지만 클래스 변수와 싱글톤에서도 같은 문제 발생 ⇒ 변수 캡슐화하기(6.6절)

## 3.6 가변 데이터

- 함수형 프로그래밍: 데이터는 절대 변하지 않고, 데이터를 변경하려면 반드시 변경하려는 값에 해당하는 복사본을 만들어서 반환한다는 개념을 기본으로 삼고 있다.
    
    [개선 하는 방법]
    
    - 정해놓은 함수를 거쳐야만 값을 수정할 수 있도록 하면 어떻게 수정되는지 감시하거나 코드를 개선하기 쉽다 ⇒ 변수 캡슐화하기(6.6절)
    - 용도별로 독립 변수에 저장하게 하여 값 갱신에 문제를 일으킬 여지를 없앤다 ⇒ 변수 쪼개기(9.1절)
    - 겡신로직은 다른 코드와 분리한다 ⇒ 문장슬라이드하기(8.6절), 함수 추출하기(6.1절)
    - API를 만들 때, 부작용이 있는 코드를 호출할 수 었도록 ⇒ 질의 함수와 변경 함수 분리하기(11.1절)
    - 세터를 호출하는 클라이언트를 찾는 것만으로 변수의 유효범위를 줄이는데 도움이 된다 ⇒ 세터 제거하기(11.7절)
    - 파생 변수를 질의 함수로 바꾸기(9.3절)
    - 변수를 갱신하는 코드들의 유효범위를 제한한다 ⇒ 여러 함수를 클래스로 묶기(6.9절), 여러 함수를 변환 함수로 묶기(6.10절)
    - 구조체러럼 내부 필드에 데이터를 담고 있는 변수라면 ⇒ 참조를 값으로 바꾸기(9.4절)

## 3.7 뒤엉킨 변경

- 코드를 수정할 때 시스템에서 고쳐야할 딱 한 군데를 찾아서 그 부분만 수정할 수 있기를 바란다.
- 단일 책임 원칙이 제대로 지켜지지 않을 때 나타난다.
- 하나의 모듈이 서로 다른 이유로 인해 여러 가지 방식으로 변경되는 일이 많을 때 발생.
    
    [개선 하는 방법]
    
    - 다음 맥락에 필요한 데이터를  특정한 데이터 구조에 담아 전달하는 식으로 단게를 분리 ⇒ 단계 쪼개기(6.11절)
    - 각 맥락에 해당하는 적당한 모듈들을 만들어서 관련 함수들을 모으기 ⇒ 함수 옮기기(8.1절)
    - 여러 맥락의 일에 관여하는 함수가 있다면 옮기기 전에 ⇒ 함수 추출하기(6.1절)
    - 모듈이 클래스라면 ⇒ 클래스 추출하기(7.5절)

## 3.8 산탄총 수술

- 뒤엉킨 변경과 비슷하면서도 정반대
- 코드를 변경할 때마다 자잘하게 수정해야 하는 클래스가 많을 때
- 변경할 부분이 코드 전반에 퍼져 있다면 찾기도 어렵고 수정해야할 곳을 지나치기 쉽다.
    
    [개선 하는 방법]
    
    - 함께 변경되는 대상 모두 한 모듈에 묶어두면 좋다 ⇒ 함수 옮기기(8.1절), 필드 옮기기(8.2절)
    - 비슷한 데이터를 다루는 함수가 많다면 ⇒ 여러 함수를 클래스로 묶기(6.9절)
    - 데이터 구조를 변환하거나 보강하는 함수들에 ⇒ 여러 함수를 변환 함수로 묶기(6.10절)
    - 이렇게 묶은 함수들의 출력결과를 묶아서 다음 단계 로직으로 전달할 수 있다면 ⇒ 단계 쪼개기(6.11절)
    - 어설프게 분리된 로직 ⇒ 함수 인라인하기(6.2절), 클래스 인라인하기(7.6절)
- 코드를 재구성하는 중간 과정에서 큰 덩어리로 뭉쳐지는 건 괜찮다.

## 3.9 기능 편애

- 어떤 함수가 자기가 속한 모듈의 함수나 데이터보다 다른 모듈의 함수나 데이터와 상호작용할 일이 많을 때 풍긴다.
- 프로그램을 모듈화할 때는 코드를 여러 영역으로 나눈 뒤 영역 안에서 이뤄지는 상호작용은 최대한 늘리고 영역 사이에서 이뤄지는 상호작용은 최소로 줄이는데 주력한다.

## 3.10 데이터 뭉치

- 데이터 항목들은 여러 곳에서 함께 뭉쳐다니는 모습을 흔히 볼 수 있는데 이렇게 몰려다니는 데이터 뭉치는 보금자리를 따로 마련해줘야 한다.
- 데이터 뭉치를 판별하는 방법: 값 하나를 삭제했을 때 나머지 데이터만으로는 의미가 없을 때 데이터 뭉치.

## 3.11 기본형 집착

- 기본형 집착(Primitive Obsession) 코드 스멜을 피하고, 도메인(Domain) 개념을 표현하는 새로운 객체를 만들라

## 3.12 반복되는 switch문

- 어떤 객체의 '타입(Type)'이나 '상태(State)'에 따라 달라지는 로직이 여러 메서드와 클래스에 걸쳐 반복적으로 switch문 또는 긴 if-else 체인 형태로 나타나는 것
- 개방-폐쇄 원칙(OCP) 위반
    - **OCP:** **확장에는 열려 있고, 수정에는 닫혀 있어야 한다.** (새로운 기능 추가는 쉬워야 하고, 기존 코드는 건드리지 않아야 한다.)
    - **Switch문 문제:** 새로운 '타입'이나 '상태'가 추가되면 (예: 새로운 제품 유형, 새로운 도형), 그 객체를 다루는 **모든** `switch`문을 찾아가서 새로운 `case`를 추가해야 합니다.
        - 이는 기존의 잘 작동하던 코드를 계속해서 **수정(modification)**하게 만들어 버그 발생 위험을 높이고 유지보수 비용을 증가시킵니다.

## 3.23 상속 포기

- 서브클래스가 부모의 동작은 필요로하지만 인터페이스는 따르고 싶지 않을 때 풍긴다.
- 구현을 따르지 않는 것은 이해할 수 있지만 인터페이스를 따르지 않는다는 것은 상당히 무례하다
    - 객체 지향적 의미와 책임을 강조하는 말입니다. 이는 **리스코프 치환 원칙 (Liskov Substitution Principle, LSP)**의 위반을 지적합니다.
    - 쉽게 말해, 상속은 **"부모 클래스는 자식 클래스로 대체될 수 있어야 한다"**는 엄격한 약속을 포함하고 있다는 의미입니다.
    
    ### 1. 🔍 구현을 따르지 않는다는 것
    
    - *'구현(Implementation)'**이란 클래스 내부의 **메서드 로직**이나 **데이터 필드**를 의미합니다.
    - **예시:** 부모 클래스가 특정 메서드를 가지고 있지만, 자식 클래스는 그 메서드의 내부 로직이 전혀 필요 없을 수 있습니다.
        - 자식 클래스가 부모의 **일부 로직을 재정의(Override)**하여 완전히 다른 방식으로 구현하거나, **아예 사용하지 않는 것**은 객체 지향적으로 허용될 수 있습니다. (구현을 따르지 않는 것)
        - 이는 상속을 통해 얻는 기능 중 **필요 없는 부분을 버리는 행위**로, 때로는 효율적일 수 있습니다.
    
    ### 2. 🚫 인터페이스를 따르지 않는다는 것 (무례함)
    
    - *'인터페이스(Interface)'**란 클래스가 외부에 **제공하는 메서드의 이름, 매개변수, 반환 타입**과 같은 **공개된 계약(Contract)**을 의미합니다.
    - **문제 상황:** 자식 클래스가 부모 클래스의 메서드를 상속받았는데, **해당 메서드를 사용하지 않거나, 잘못된 로직으로 만들어 버려서** 부모 클래스의 의도된 동작을 전혀 수행하지 못하게 만드는 경우입니다.
    - **리스코프 치환 원칙 (LSP) 위반:** 이 원칙은 "자식 클래스의 인스턴스는 부모 클래스의 인스턴스를 **대신하여** 사용될 수 있어야 한다"고 명시합니다.
        - *"무례하다"**는 것은 바로 이 **LSP 약속을 깼다**는 뜻입니다. 부모 타입의 객체가 필요한 곳에 자식 타입의 객체를 넣었더니, **예상치 못한 동작**을 하거나 **오류(예: 예외 발생)**를 일으켜서 프로그램 전체를 망가뜨리는 상황을 말합니다.
    - **예시:** 부모 클래스가 `pay()`라는 메서드를 정의했는데, 서브 클래스가 이 `pay()` 메서드에서 예외를 발생시키거나, 엉뚱한 로그만 남기는 경우입니다. 부모 클래스(`Payment`)를 기대하고 `pay()`를 호출한 클라이언트 코드는 제대로 결제가 이루어지지 않는다는 점에서 혼란과 버그를 겪게 됩니다.
    
    ---
    
    ### 💡 핵심: 상속은 곧 'is-a' 관계
    
    이 문구가 강조하는 것은 **상속은 'A는 B이다 (A is-a B)'라는 관계**를 엄격하게 만족해야 한다는 점입니다.
    
    부모 클래스를 상속받는 서브 클래스는 "나도 부모처럼 행동할 수 있어요"라고 외부에 약속하는 것과 같습니다. 이 약속을 깨고 인터페이스를 통해 제공되는 핵심 기능을 무시하는 것이 바로 "상당히 무례하다"는 표현으로 지적되는 것입니다.

- 아예 상속메커니즘을 벗어나기
    - 서브클래스를 위임으로 바꾸기(12.10절)
    - 수퍼클래스를 위임으로 바꾸기(12.11절)

## 3.24 주석

- 주석이 많으면 잘못 작성된 경우가 많다.
    
    [개선 하는 방법]
    
    - 특정 코드 불록이 하는 일에 주석을 남기고 싶다면 ⇒ 함수 추출하기(6.1절)
